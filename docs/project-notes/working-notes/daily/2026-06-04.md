## Week 5 dashboard direction

Alex said the Week 5 plan felt too dense because he is a novice to software development and these systems are new. Continuing AvalonReach work should explain terms plainly, choose one feature area at a time, and save the reasoning and changes in project notes.

Chosen first Week 5 focus: dashboard / saved results.

Plain-language product direction:

- A dashboard means the place a returning user goes to see saved AvalonReach searches, saved recommendations, update preferences, and eventually provider follow-up links.
- Avoid "heavy auth" for the first Week 5 pass. In this context, heavy auth means a full login/account system with passwords or magic links, Supabase Auth settings, redirect URLs, sessions, account recovery, and profile-management edge cases.
- Start with email-based lookup because it is easier to build and easier to demonstrate: a user enters an email after a search, AvalonReach stores the saved result, and later the user can look up saved results by email.
- Keep the design open for username creation later. Alex may want unique usernames because emails can change over time, especially for people moving addresses.
- Avoid brittle user profile design. Alex cited AT&T account/profile trouble where broken profiles sometimes required building a whole new account. AvalonReach should avoid coupling everything to one fragile account record.

Recommended first implementation path:

1. Add a small `user_profiles` or `saved_users` concept with stable internal ID.
2. Let saved results connect to that stable ID.
3. Use email as the first lookup method.
4. Reserve unique username as an optional profile field later.
5. Do not require full login/auth until there is a strong reason.

Open decision for later:

- Whether unique usernames should be public-facing handles, private recovery identifiers, or both.

## Use My Location feedback fix

Alex raised a privacy/usability issue: when a user chooses "Use my location," the results page previously just showed results without telling the user what location had been used. Coordinates are not useful feedback for most users, and a VPN or bad device location signal could make results wrong.

Clarified behavior:

- The app uses browser/device geolocation through `navigator.geolocation`.
- AvalonReach is not intentionally doing its own IP address lookup for this feature.
- Browser location can still be based on GPS, Wi-Fi, cell-tower, or IP-based signals depending on device/browser settings.
- VPNs or stale device location can produce wrong results, so users need a plain warning and an address-based correction path.

Implemented:

- Added Census reverse-geography lookup for coordinate searches so the app can show a useful label like `Device location near Philadelphia, PA` instead of raw latitude/longitude.
- Added a "Location used" feedback panel on the results page when location coordinates are used.
- The panel explains that the browser shared approximate device location, that VPN/device location can be wrong, and that entering the service address is the most accurate path.
- Updated the coordinate lookup notice to mention browser-shared device location and VPN risk.
- Updated the privacy page to explain Use My Location, browser permission, possible location sources, and the address-entry alternative.
